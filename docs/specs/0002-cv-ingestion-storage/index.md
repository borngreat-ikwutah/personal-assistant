# 0002. CV ingestion and storage

**Date**: 2026-11-07
**Status**: In Progress

## Summary

This feature stores one private CV in R2 while keeping immutable version metadata in D1. An authenticated Worker endpoint accepts PDF or DOCX uploads up to 10 MB. Every successful upload becomes the current version, while existing application records keep the version they used. Trigger.dev tasks read the selected version directly from R2 through the S3 compatible API.

## Requirements

**User stories**:
- As the operator, I want to upload a CV through one authenticated endpoint, so the agent can use it without exposing the file publicly.
- As the operator, I want each upload preserved as a version, so a new CV cannot change the evidence used for an older application.
- As an agent task, I want to fetch an exact CV version by its object key, so matching and later submission use a known document.

**Acceptance criteria**:
- **AC-1**: A private R2 bucket is bound to the Worker as `CV_FILES`, and the generated Worker bindings include it.
- **AC-2**: `POST /cv` requires the `API_SECRET` header, accepts a multipart `file`, allows PDF and DOCX only, rejects files over 10 MB, and returns typed metadata for the created version.
- **AC-3**: A successful upload writes the bytes to R2 under a generated immutable key and writes matching metadata to D1. The R2 object is never publicly addressable.
- **AC-4**: Every successful upload creates an immutable version. The newest successful version becomes current, while prior versions remain readable and unchanged.
- **AC-5**: `GET /cv` requires `API_SECRET` and returns the current version plus a paginated version list without returning file bytes or secrets.
- **AC-6**: Repeating an upload with the same required `Idempotency-Key` returns the original version metadata without creating a second version or replacing its object.
- **AC-7**: A Trigger.dev task can fetch a selected version using its stored R2 bucket and object key through the R2 S3 compatible API, with credentials supplied only through Trigger.dev secrets.
- **AC-8**: A failed D1 write after an R2 upload attempts to delete the newly written object and does not advance the current version pointer. A failed R2 write creates no D1 version.
- **AC-9**: A CV version referenced by an application payload remains available. The MVP exposes no deletion operation and retains all versions indefinitely.
- **AC-10**: Invalid authentication, missing files, unsupported formats, oversized files, malformed metadata, and missing version identifiers return stable typed errors without leaking file contents or credentials.

## Decision

The Worker owns ingestion and writes to the Cloudflare R2 binding. D1 stores the logical CV record and immutable version metadata. Each upload has a generated object key, a SHA 256 digest, an idempotency key, size, content type, original filename, and upload time. A singleton logical document points to the current version.

R2 remains private. Trigger.dev tasks use R2's S3 compatible API for direct reads, so large CV files do not pass through the Worker. R2 API credentials exist only in Trigger.dev environment configuration. The Worker uses its binding and never returns a public URL.

## Feature design

**Data model sketch**:

`cv_documents`
- `id` TEXT primary key, fixed value `primary`
- `current_version_id` INTEGER nullable foreign key to `cv_versions.id`
- `created_at` TEXT required
- `updated_at` TEXT required

`cv_versions`
- `id` INTEGER primary key, auto increment
- `document_id` TEXT required, foreign key to `cv_documents.id`
- `object_key` TEXT required, unique, generated by the Worker
- `original_filename` TEXT required
- `content_type` TEXT required, limited to the accepted PDF and DOCX MIME values
- `size_bytes` INTEGER required, between 1 and 10 MB inclusive
- `sha256` TEXT required
- `idempotency_key` TEXT required, unique
- `created_at` TEXT required

Relationships:

| Entity | Relationship | Foreign key |
|---|---|---|
| `cv_documents` to `cv_versions` | one document has many versions | `cv_versions.document_id` |
| `cv_documents` to current version | one document points to zero or one current version | `cv_documents.current_version_id` |
| `applications` to CV version | an application payload may reference one immutable version | existing JSON `payload.cv_version_id` contract |

The R2 object key is `cv/versions/<version id or UUID>/<sanitized extension>`. The key is opaque to callers and is stored in D1 for task access. The singleton document row is seeded on first upload.

**State transitions**:

```text
no CV → version 1 current
current version N → version N+1 current
```

Versions never change state and are never deleted in the MVP. If ingestion fails, the attempted version does not become current.

**API surface**:

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/cv` | POST | multipart `file` required, `Idempotency-Key` header required | version id, current flag, filename, content type, size, digest, created time | `API_SECRET` header | 401, 409 idempotency conflict, 413 too large, 415 unsupported type, 422 invalid upload |
| `/cv` | GET | `limit` optional 1 to 100, `offset` optional nonnegative | current version metadata, total, limit, offset, version metadata list | `API_SECRET` header | 401, 422 invalid pagination |
| `/cv/:versionId` | GET | positive version id | selected version metadata | `API_SECRET` header | 401, 404 missing version, 422 invalid id |

The metadata endpoint does not stream a file or produce a public URL. Trigger.dev tasks use the task helper and the stored object key for file reads.

**Value sourcing**:

| Action | Value produced or displayed | Source |
|---|---|---|
| upload response | version id | D1 generated primary key |
| upload response | current flag | successful current pointer update |
| upload response | filename and content type | validated multipart file metadata |
| upload response | size | uploaded byte length |
| upload response | digest | Worker SHA 256 calculation over uploaded bytes |
| upload response | created time | Worker generated ISO timestamp |
| object location | R2 object key | Worker generated opaque version key |
| current CV read | current metadata | `cv_documents.current_version_id` joined to `cv_versions` |
| version list | order and pagination | `cv_versions.created_at`, `limit`, and `offset` request values |
| task file read | bucket and object key | Trigger.dev environment bucket name plus selected `cv_versions.object_key` |
| historical application CV | exact version identity | existing `applications.payload.cv_version_id` written by the later matching or submission flow |

**Key invariants**:
- R2 objects are private and every object has exactly one D1 version metadata row after successful ingestion.
- Every object key and idempotency key is unique.
- A current pointer always references a version belonging to the singleton document.
- Version metadata and bytes are immutable after creation.
- The current pointer advances only after the R2 write succeeds and the D1 metadata write succeeds.
- A retry with the same idempotency key returns the original version and does not create another object.
- Applications retain the exact CV version they used through `payload.cv_version_id`.
- No endpoint returns raw CV bytes or credentials.

**Security model**:

This is a single actor feature. Upload and metadata reads require the existing `API_SECRET` header. The R2 bucket is private, and object keys are not accepted as public URLs. CV files are personal data, so logs must contain version ids and sizes only, never file contents, raw multipart bodies, object credentials, or full object URLs containing secrets. Trigger.dev credentials are read only from its environment and are not stored in D1 or Worker variables.

**Configuration required**:
- `CV_FILES`: private R2 bucket binding used by the Worker.
- `R2_ACCOUNT_ID`: Trigger.dev secret used to form the R2 S3 compatible endpoint.
- `R2_ACCESS_KEY_ID`: Trigger.dev secret for read access to the CV bucket.
- `R2_SECRET_ACCESS_KEY`: Trigger.dev secret for read access to the CV bucket.
- `R2_BUCKET_NAME`: Trigger.dev environment value naming the bound bucket.

**Critical test scenarios**:
- Happy path: upload a valid PDF, read current metadata, upload a second version, and confirm both versions remain listed while the second is current, verifies **AC-2**, **AC-3**, **AC-4**, **AC-5**.
- Idempotency: repeat the same upload request with the same idempotency key and confirm one D1 row and one R2 object, verifies **AC-6**.
- Failure case: force an R2 or D1 failure and confirm no incorrect current pointer and cleanup attempt, verifies **AC-8**.
- Validation: missing file, unsupported type, 10 MB plus one byte, malformed pagination, and missing version each return their documented error, verifies **AC-10**.
- Auth: requests without `API_SECRET` cannot upload or read CV metadata, verifies **AC-2**, **AC-5**, **AC-10**.
- Task access: a Trigger.dev task fetches the selected object using its D1 key and returns only a digest or byte count in the test harness, verifies **AC-7**.

## Consequences

**Positive**:
- Historical applications can always identify the exact CV version used.
- R2 handles binary storage while D1 remains the typed source for metadata and version selection.
- Trigger.dev can read files without proxying them through the Worker.
- Idempotency prevents network retries from producing duplicate versions.

**Negative / tradeoffs**:
- Trigger.dev needs a separate R2 credential set and environment configuration.
- A failed cross service write can briefly create an orphan object, so cleanup and later reconciliation must be observable.
- Permanent retention increases storage over time and requires a later deletion policy.
- The Worker must buffer uploads to calculate the digest and enforce the 10 MB limit.

**Neutral**:
- CV text extraction is intentionally deferred to application intelligence.
- Multiple CV profiles are deferred; the singleton document can be generalized later without changing version immutability.
